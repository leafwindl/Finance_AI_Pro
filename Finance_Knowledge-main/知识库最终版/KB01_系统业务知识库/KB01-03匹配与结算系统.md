## 功能名称和目的  
**功能名称**：实时限价/市价订单匹配与结算系统（Real-time Limit/Market Order Matching & Settlement System）  
**功能目的**：  
- 实现符合 HOSE（胡志明证券交易所）机制的连续撮合交易逻辑，支持买卖双方订单的动态价格发现与自动执行；  
- 保障用户虚拟资产（现金余额、持股数量、交易历史）在订单成交后原子性、一致性更新；  
- 为教育场景提供真实市场微观结构（order book, price formation, supply-demand dynamics）的可验证模拟环境。  
*依据来源：Chapter 1.2 “Core Trading Functionality”；Chapter 4.3.0.6 “orderMatchingService.js” & “orderSettlementService.js”；Abstract*

## 使用角色或调用方  
- **终端用户（Role: `user`）**：通过 Trade 页面提交 Buy/Sell 订单（Market/Limit 类型）；  
- **系统后台（Backend Service）**：`orderMatchingService.js` 自动触发撮合，`orderSettlementService.js` 执行结算；  
- **管理员（Role: `admin`）**：通过 Admin 页面控制交易时段（Open/Close Session），间接影响订单可提交状态。  
*依据来源：Chapter 3 “UI/UX Design” (Fig 3.10, 3.11)；Chapter 4.3.0.6 “tradingSessionService.js”；Chapter 5.3.1 RBAC 矩阵*

## 操作入口  
- **前端入口**：Trade 页面的交互式交易表单（Fig 3.10）：  
  - 输入框：Stock Symbol（如 AAPL）、Action（Buy/Sell）、Quantity、Order Type（Limit/Market）；  
  - 按钮：“Place Order”（提交）、“Clear”（重置）。  
- **后端入口**：REST API `/api/orders`（POST），由 `routes/orderRoutes.js` 定义，经 `middleware/orderValidationMiddleware.js` 预检后路由至 `controllers/orderController.js`。  
*依据来源：Chapter 3 Fig 3.10；Chapter 4.3.0.5 “routes”；Chapter 4.3.0.3 “orderValidationMiddleware”*

## 前置条件  
1. **用户已认证**：JWT Access Token 有效（`authenticationMiddleware` 验证）；  
2. **交易时段开放**：`tradingSessionService.js` 返回 `sessionStatus === 'OPEN'`（`tradingSessionMiddleware` 检查）；  
3. **订单参数合规**：  
   - *Limit Order*：价格 ∈ [Floor Price, Ceiling Price]（7% 波动限制）；  
   - *Sell Order*：`quantity ≤ user's current holdings`（`orderValidationMiddleware` 校验）；  
   - *Buy Order*：`cash_balance ≥ quantity × price`（资金充足性校验）；  
4. **数据库就绪**：PostgreSQL 中 `Users`, `Portfolios`, `Holdings`, `Stocks`, `StockPrices` 表数据完整（`config/` 初始化脚本保障）。  
*依据来源：Chapter 1.2 “Core Trading Functionality”；Chapter 4.3.0.3 “orderValidationMiddleware”；Chapter 4.3.0.1 “config”*

## 正常处理  
|步骤|操作/输入|系统处理|输出|
|---|---|---|---|
|1|用户提交 Buy Limit Order（AAPL, Qty=10, Price=170）|`orderController.js` 调用 `orderCRUDService.js` 创建未匹配订单记录；`orderMatchingService.js` 启动撮合流程|返回 HTTP 201，响应体含 `order_id`, `status: 'PENDING'`|
|2|`orderMatchingService.js` 扫描 Order Book|按优先级规则比对：Buy Limit（高价优先）vs Sell Limit（低价优先）；若存在 `ask_price ≤ 170` 的 Sell 订单，则匹配|生成 Match Event（含成交价、成交量）|
|3|匹配成功（如：Sell @160, Qty=5）|调用 `orderSettlementService.js`：<br>• 扣减 Buyer 现金：`100000 → 100000 - (5×160)`<br>• 增加 Buyer 持股：`Holdings.quantity += 5`<br>• 扣减 Seller 持股：`Holdings.quantity -= 5`<br>• 增加 Seller 现金：`+ (5×160)`<br>• 写入 `Transactions` 表（BUY/SELL 记录）|返回 HTTP 200，响应体含 `matched_part`, `unmatched_part`（若部分成交）|
|4|匹配失败（无满足条件的对手单）|将订单持久化至 `OrderBook`（内存+DB），加入对应价格队列（Buy Queue / Sell Queue）|返回 HTTP 201，`status: 'IN_BOOK'`，前端实时渲染 Order Book 更新|

## 异常和边界  
|场景|触发条件|预期处理|
|---|---|---|
|**资金不足**|Buy Limit Order 的 `quantity × price > user.cash_balance`|`orderValidationMiddleware` 拦截，返回 HTTP 400，错误信息 `"Insufficient balance"`|
|**持仓不足**|Sell Order 的 `quantity > Holdings.quantity`（针对该 stock_id）|`orderValidationMiddleware` 拦截，返回 HTTP 400，错误信息 `"Insufficient stock holdings"`|
|**价格越界**|Limit Order 的 `price < Floor` 或 `price > Ceiling`（基于 Reference Price ±7%）|`orderValidationMiddleware` 拦截，返回 HTTP 400，错误信息 `"Price outside ceiling/floor bounds"`|
|**会话关闭**|`tradingSessionService.js` 返回 `CLOSED`，用户仍提交订单|`tradingSessionMiddleware` 拦截，返回 HTTP 403，错误信息 `"Trading session is currently closed"`|
|**部分成交**|Buy @170, Qty=9 匹配 Sell @160, Qty=5|系统自动拆分订单：<br>• `matched_part`: Qty=5, Price=160<br>• `unmatched_part`: Qty=4, Price=170（存入 Buy Queue）<br>• 两部分均写入 `Transactions` 表（状态区分）|

## 输入、输出和状态变化  

**输入**：  
- HTTP Request Body（JSON）：`{ "stock_symbol": "AAPL", "action": "BUY", "quantity": 10, "order_type": "LIMIT", "price": 170 }`  
- 系统参数：`Reference Price`（来自 `StockPrices` 表最新日数据）、`Ceiling/Floor`（`Ref × 1.07` / `Ref × 0.93`）  

**输出**：  
- HTTP Response（JSON）：包含 `order_id`, `status`, `matched_part`, `unmatched_part`, `execution_time`；  
- 前端 UI：Order Book 实时刷新（Bid/Ask/Mid）、Portfolio 页面现金/持股数即时更新、Transaction History 新增记录。  

**状态变化**：  
- `Portfolios.cash_balance`（Buy 减 / Sell 加）；  
- `Holdings.quantity`（Buy 加 / Sell 减）；  
- `Transactions` 表新增行（含 `portfolio_id`, `stock_id`, `transaction_type`, `quantity`, `price`）；  
- `OrderBook` 内存结构更新（Buy/Sell Queue 重排序或新增节点）。  

## 关联知识  

**关联规则**：  
- **价格规则**：`Ceiling = Ref × 1.07`, `Floor = Ref × 0.93`（Chapter 1.2 “Dynamic Price Calculation”）；  
- **撮合规则**：Buy Limit（高价优先）、Sell Limit（低价优先）、First-In-First-Out（FIFO）于同价位（Chapter 4.3.0.6 “orderMatchingService.js”）；  
- **RBAC 规则**：仅 `admin` 可调用 `/api/admin/session/open`（Chapter 5.3.1 `ROLE_PERMISSIONS`）。  

**关联流程**：  
- 用户注册 → `initUserUtil.js` 初始化 `$100,000` 现金 + `10 shares` 各股票（Chapter 4.3.0.7 “initUserUtil.js”）；  
- 订单提交 → `orderValidationMiddleware` → `orderController` → `orderMatchingService` → `orderSettlementService`（Chapter 4.3 Backend Workflow）；  
- 结算完成 → 触发 `ItemStatusActionSSE` 推送实时价格/持仓变更（Chapter 2.1.5 “Server-Sent Events”）。  

**关联接口**：  
- Frontend → Backend：`POST /api/orders`（Chapter 4.3.0.5 “routes”）；  
- Backend → Database：`pg` client 查询 `StockPrices`（获取 Ref）、更新 `Portfolios`/`Holdings`/`Transactions`（Chapter 2.2.2 “PostgreSQL”）；  
- Backend → External：`Sepay API`（仅用于 Fund Top-up，非本功能直接关联，故不列入）。

**模拟声明**：  
- 本功能**完全模拟真实交易所连续竞价机制**，但**不涉及真实资金清算**（所有交易在虚拟账户内闭环）；  
- **价格波动限制（7%）**、**订单簿结构（Bid/Match/Ask）**、**撮合优先级规则** 均严格复现 HOSE 规范（Chapter 1.2 “Core Trading Functionality”）；  
- **状态一致性** 通过 PostgreSQL 事务（`BEGIN...COMMIT`）保障，避免中间态（Chapter 2.2.2 “PostgreSQL v16.1” 高可靠性特性）。
