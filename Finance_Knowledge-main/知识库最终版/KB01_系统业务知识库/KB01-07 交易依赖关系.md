## 当前模块或功能  
Trading Session Controller（交易时段控制器）—— 管理全局交易开关状态，位于 `controllers/tradingSessionController.js`，供 Admin 页面调用 `openSession()`/`closeSession()`，并为所有订单路由提供状态检查。  

## 依赖清单  
|依赖系统/模块|依赖内容|调用方向|必需/可选|  
|---|---|---|---|  
|`tradingSessionService.js`|提供 `openSession()`, `closeSession()`, `isSessionOpen()` 方法，内部维护 Redis 缓存与 PostgreSQL 持久化|同步调用|必需|  
|`Redis`（隐式）|`tradingSessionService` 使用 Redis 存储实时会话状态（key: `trading:status`），实现毫秒级读取|读写调用|必需|  
|`RoleBasedAccessControlMiddleware`|校验调用者角色为 `ADMIN`（`ROLE_HIERARCHY.ADMIN`）|前置校验|必需|  
|`PostgreSQL`|`tradingSessionService` 将开关事件写入 `trading_sessions` 表（审计日志）|异步写入|必需|  

## 正常调用顺序  
1. Admin 发起 `POST /api/admin/session/open` →  
2. `RoleBasedAccessControlMiddleware` 验证 `req.user.role === 'admin'` →  
3. `tradingSessionController.openSession()` 调用 `tradingSessionService.openSession()` →  
4. `tradingSessionService` 同时：  
　　a) 设置 Redis `trading:status = "OPEN"`（EX 300s）；  
　　b) 插入 PostgreSQL `trading_sessions` 记录；  
5. 前端 `TradingSessionContext` 通过 SSE 或轮询获取状态变更。  

## 依赖不可用时的处理  
|异常|处理方式|是否重试|对用户/业务的影响|  
|---|---|---|---|  
|Redis 不可用|降级为直读 PostgreSQL `trading_sessions` 最新记录（性能下降，但状态不丢失）|否|Admin 操作延迟（~200ms），用户端状态刷新延迟 ≤ 5s|  
|PostgreSQL 写入失败|记录错误日志，但允许 Redis 状态变更成功（最终一致性：后台任务补写）|是（后台重试）|审计日志缺失，但交易开关功能不受影响|  
|`RoleBasedAccessControlMiddleware` 失效|请求被 `express` 拦截，返回 `401 Unauthorized`|否|非 Admin 用户无法访问任何 `/admin/session/*` 接口，零权限泄露风险|  

## 数据一致性和超时要求  
- **最终一致性**：Redis（主）与 PostgreSQL（源）之间允许 ≤ 1s 差异；  
- **超时阈值**：Redis `SET` 操作 ≤ 50ms；PostgreSQL `INSERT` ≤ 100ms；  
- **幂等设计**：`openSession()` 多次调用仅产生一条 PostgreSQL 记录（`ON CONFLICT DO NOTHING`）。  

## 建议测试场景  
- 【安全】非 Admin 用户尝试 `POST /api/admin/session/close`，验证 401 响应且无日志泄露；  
- 【高可用】Kill Redis 容器，验证系统自动切换至 PostgreSQL 读取，Admin 操作仍成功；  
- 【审计】检查 `trading_sessions` 表是否完整记录每次开关操作的 `admin_id`, `timestamp`, `status`；  
- 【前端同步】验证前端 `TradingSessionContext` 在 Redis 状态变更后 ≤ 1s 内触发 UI 刷新（SSE 测试）。
