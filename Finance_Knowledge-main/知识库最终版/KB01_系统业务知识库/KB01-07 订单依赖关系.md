## 当前模块或功能  
Order Matching Engine（订单匹配引擎）—— 实现连续竞价模式下的限价单撮合逻辑，位于 `services/orderMatchingService.js`，负责 Bid/Ask 队列管理、价格优先/时间优先匹配、部分成交拆分及结算触发。  

## 依赖清单  
|依赖系统/模块|依赖内容|调用方向|必需/可选|  
|---|---|---|---|  
|`PostgreSQL v16.1`|读取实时 Order Book 数据（`orders` 表）、写入匹配结果与交易记录（`transactions`, `holdings`, `portfolios` 表）|同步调用|必需|  
|`orderSettlementService.js`|触发成交后资金与持仓更新（调用 `updateUserBalance`, `updateUserHoldings`）|同步调用|必需|  
|`tradingSessionService.js`|查询当前交易时段状态（`isSessionOpen()`）|同步调用|必需|  
|`stockPriceService.js`（隐式）|获取股票最新 `ceiling/floor` 价格（用于 Limit 订单校验，由 `orderValidationMiddleware` 提前注入）|前置校验|必需|  

## 正常调用顺序  
1. 接收新订单（Buy/Sell）→  
2. 校验 `tradingSessionService.isSessionOpen()` →  
3. 查询 `stockPriceService` 获取 `ceiling/floor` →  
4. 加入对应 Bid/Ask 队列 →  
5. 扫描队列执行匹配（价格优先+时间优先）→  
6. 若匹配成功，调用 `orderSettlementService` 更新双账户 →  
7. 写入 `transactions`, `holdings`, `portfolios` 至 PostgreSQL。  

## 依赖不可用时的处理  
|异常|处理方式|是否重试|对用户/业务的影响|  
|---|---|---|---|  
|PostgreSQL 连接失败|捕获 `pg` 错误，返回 `503 Service Unavailable`，记录 `loggerUtil` 错误日志|否（连接级故障）|所有订单无法提交/匹配，交易中断，用户看到“系统繁忙”提示|  
|`orderSettlementService` 调用超时（>2s）|回滚本次匹配事务（`ROLLBACK`），将未匹配订单重新入队|否（幂等性保障）|单笔订单延迟或失败，但订单书状态一致，用户需重试下单|  
|`tradingSessionService` 返回 `false`|直接拒绝订单，返回 `403 Forbidden` + “交易时段已关闭”|否|用户无法下单，但界面可实时显示“休市中”，无资金/持仓风险|  

## 数据一致性和超时要求  
- **强一致性要求**：匹配与结算必须原子执行（通过 PostgreSQL `BEGIN...COMMIT` 事务包裹）；  
- **超时阈值**：单次匹配操作 ≤ 800ms（因涉及多表写入与锁竞争）；  
- **最终一致性补偿**：若结算服务失败，后台 `cron` 任务每 5 分钟扫描 `pending_orders` 表补发结算请求。  

## 建议测试场景  
- 【高危】模拟 PostgreSQL 主库宕机，验证订单入队缓存与降级只读模式；  
- 【核心】并发 500+ 限价单涌入，验证 Bid/Ask 队列锁粒度与匹配吞吐；  
- 【边界】Sell 订单量 > 用户当前持仓，验证 `orderValidationMiddleware` 提前拦截（非匹配层拦截）；  
- 【异常】人工关闭交易时段后，验证新订单被 `tradingSessionMiddleware` 拦截，且历史订单仍可查询。
