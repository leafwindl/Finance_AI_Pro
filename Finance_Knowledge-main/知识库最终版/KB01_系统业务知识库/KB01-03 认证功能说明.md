## 功能名称和目的
> **冲突待核验：** 本文描述 JWT Access+Refresh 认证链路，与 KB01-03 用户认证与会话管理（OTP+设备信任）、KB01-03 登录功能说明（Google OAuth2 SSO）并存，登录主链路待代码核验；Cookie 与 Authorization Bearer 两种传递方式并存（见 00_业务口径冲突清单-登录链路项）。

**功能名称**：JWT（JSON Web Token）认证与会话管理  
**目的**：实现无状态、可扩展的用户身份认证；通过双Token（Access+Refresh）机制，在保障短期会话安全的同时，支持长期用户在线，彻底规避传统Session服务器的单点故障与水平扩展瓶颈。

## 使用角色或调用方
- **前端用户**：通过浏览器接收并自动携带JWT Cookie。
- **后端服务**：`authMiddleware.js`（鉴权中间件）、`userService.js`（登录签发）、`utils/jwt.js`（Token工具）。

## 操作入口
- **签发入口**：`userService.loginUserService` 成功后调用 `generateTokens(payload)`。
- **鉴权入口**：所有受保护路由（如 `/api/portfolio`）均需经过 `authMiddleware` 拦截。

## 前置条件
- 环境变量 `JWT_SECRET`（主密钥）、`ACCESS_SECRET`（Access Token专用密钥）已安全配置于 `.env` 文件，**绝不可硬编码或暴露在客户端**。
- `ACCESS_EXPIRES_IN`（如 `"15m"`）与 `REFRESH_EXPIRES_IN`（如 `"7d"`）已定义，分别控制两种Token有效期。
- 前端必须启用 `withCredentials: true`（Axios）或 `credentials: 'include'`（Fetch），以支持跨域Cookie传输。

## 正常处理
|步骤|操作/输入|系统处理|输出|
|---|---|---|---|
|1|用户登录成功 | 调用 `generateTokens(payload)`：<br>• `payload` 含 `id`, `username`, `email`, `role` 及 `login_at` 时间戳<br>• 使用 `ACCESS_SECRET` 签发Access Token（短时效）<br>• 使用 `REFRESH_SECRET` 签发Refresh Token（长时效） | 两个独立JWT字符串 |
|2|将Token返回客户端 | Access Token存入 `httpOnly`, `secure`, `sameSite=strict` Cookie；Refresh Token同理存储（项目中暂存于内存全局变量） | 客户端浏览器获得两个加密Cookie |
|3|客户端访问受保护路由 | 浏览器自动在请求头附带 `Cookie: jwt=<access_token>` | 请求抵达服务器 |
|4|`authMiddleware` 处理请求 | ① 从Cookie或 `Authorization: Bearer <token>` 提取Token；<br>② 调用 `jwt.verify(token, JWT_SECRET)` 验证签名与有效期；<br>③ 解析Payload，将用户信息挂载至 `req.user` | `req.user` 对象（含ID、角色等），供后续路由使用 |

## 异常和边界
|场景|触发条件|预期处理|
|---|---|---|
|**Access Token过期**| 客户端携带的Access Token `exp` 字段已过期 | `authMiddleware` 返回 `401 Unauthorized`，前端捕获后应自动发起Refresh Token请求。 |
|**Refresh Token失效**| Refresh Token 过期、被篡改、或服务端内存中记录丢失 | 服务器拒绝签发新Access Token，前端必须重定向至登录页，强制用户重新认证。 |
|**Cookie未发送**| 前端请求未设置 `credentials: 'include'`，或跨域Origin不匹配 | `authMiddleware` 因无法获取Token而返回 `401`。原文强调：`cors` 配置中 `credentials: true` 是Cookie跨域生效的强制前提。 |

## 输入、输出和状态变化

**输入**：  
- 用户身份信息（`payload`）  
- JWT密钥（`ACCESS_SECRET`, `JWT_SECRET`）  
- Token有效期配置（`ACCESS_EXPIRES_IN`）  

**输出**：  
- Access Token（短时效JWT，用于API鉴权）  
- Refresh Token（长时效JWT，用于续期）  
- `req.user` 对象（鉴权后注入请求上下文）  

**状态变化**：  
- 用户会话状态由“临时凭证”升级为“已解析身份”，可在任意路由中通过 `req.user` 获取权限信息。  
- 服务端无状态：所有会话信息均编码于Token内，不依赖本地Session存储。  

## 关联知识

**关联规则**：  
- **`httpOnly` 标志**：阻止JavaScript访问Cookie，是防御XSS窃取Token的关键防线。  
- **`sameSite=strict`**：防止CSRF攻击，确保Cookie仅在同站请求中发送。  
- **双Token分离**：Access Token不存于服务端，Refresh Token需服务端校验（项目中暂存内存，生产应存DB）。  

**关联流程**：  
- Token签发：`login → generateTokens → sign(Access) + sign(Refresh) → Set-Cookie`  
- Token刷新：`401 → Frontend sends Refresh Token → Backend verifies & issues new Access Token`  

**关联接口**：  
- `jwt.sign(payload, secret, { expiresIn })`  
- `jwt.verify(token, secret)`
