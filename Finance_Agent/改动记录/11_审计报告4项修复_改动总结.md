## 每项简述

### 1. 编排器报告取值（中1）

- **改前**：`result.test_analysis = analysis_result.get("aggregated_context", "")` —— `aggregated_context` 只是四库检索原文，不是报告；且传给 agent4 前被截成 200 字符。
- **改后**：从 `analysis_result["messages"][-1]` 提取 `rag_response`/`chat_response` 写入的六维报告（str / list 分段 / str() 兜底，与 `src/api/server.py:346-361` 逐行一致）；完整报告直接传给 agent4。
- **影响面**：`FullPipeline` 只被 CLI 与测试使用，不在 Web 调用链。

### 2. 附件文本重复塞入（中3）

- **改前**：`_query_with_attachments` 把附件拼进 query，agent1/agent5 分支又把同一批文本放进 `file_content` → LLM 看两遍（agent5 的 messages+query+file_content 共三遍）。
- **改后**：新增 `raw_query = req.query`，agent1/agent5 的 `requirement_input`/`query`/`messages` 用原始 query；附件只经 `file_content`（与 agent1 自身 `/review` 入口契约一致；agent5 意图路由依赖 `file_content`，故保留该字段）。
- **影响面**：SSE 五事件结构未动，后端审批双写、前端渲染、OCR 文本通道（`attachments[].text → file_content`）均不受影响。

### 3. KB 路由空查询兜底（中4）

- **改前**：`has_routing` 只判断 `kb_code_list` 非空；LLM 输出"成功但内容异常"（关键词空 / 未知代码值如 `["KB01"]`）时四查询全空、`all_query=None` → 返回"（本轮未触发知识库检索）"，需求被静默丢弃。
- **改后**：四查询全空时 `all_query = origin_query` 走既有全库检索分支并打印 `[警告]`。正常路由路径零变化，兜底仅多 1 次毫秒级 KB 请求。
- **依据**：同项目同模型（DeepSeek）有 prompt 格式偏离实测先例（档案 04：agent3 检查项 18/18 失败；档案 06：agent1 结构化输出异常降级）。

### 4. 步骤序号类型校验（中6）

- **改前**：只转 `str`，`1.0`/`True`/`"abc"`/`None` 原样漏过 → `reply_node` 直接 f-string 进 markdown 表格。
- **改后**：规整（strip 后 `int()`；整数值 float → int）后要求 `type(step_no) is int`（同时排除 bool 子类），不合法则明确报错走 `gen_error_node` 分支。
- **影响面**：`step_no` 只在 agent4 图内消费；合规输入渲染无变化，SSE 契约不变。

## 跨部件一致性检查结论

改动全部在 `Finance_Agent` 内部，经全链路契约追踪确认与前端（Vue）/ 后端（FASTAPI 网关）/ 知识库（KB 服务）无矛盾：

- 网关 SSE 五事件（progress/delta/approval_required/completed/error）结构未变；
- 后端发往 Agent 平台的请求体（原始 query + attachments 分离）契约未变；
- agent2/3/4 的附件拼接、KB 检索路径未动；
- `FullPipeline` 不在 Web 调用链。
